# P2 WS4' — gateway: payment and ledger routes

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** the gateway routes every `payment.yaml` and `ledger.yaml` operation to the right upstream with the right auth level, and provider callbacks reach payment-svc unchanged.

**Architecture:** add two upstreams (`payment`, `ledger`) and a fourth auth level, `Callback`, to the existing static route table. A `Callback` route never verifies a token and never injects identity, so a stale `Authorization` header on a provider return URL is ignored rather than answered with 401. Everything else (the pipeline, middleware order, proxy, rate limits) stays as in P1. The pass-through guarantees already hold in the P1 proxy; P2 only pins them with tests.

**Tech Stack:** Go 1.27, `net/http/httputil` ReverseProxy (Rewrite mode), testify.

**Spec:** `docs/superpowers/specs/2026-09-29-marketplace-p2-ws4-gateway.md` (and the P2 overview). Worktree `../E-Commerce-p2-ws4-gateway`, branch `p2-ws4-gateway`.

## Global Constraints

- Contracts in `api/` and `gen/` are frozen. Edit only `services/gateway/` (plus this plan).
- P1 rulings stay: non-canonical paths and methods outside GET/HEAD/POST/PUT/PATCH/DELETE/OPTIONS → 404 NOT_FOUND; trusted-proxy handling (`TRUSTED_PROXIES`, X-Forwarded-For only from a trusted peer) is unchanged.
- Rate limit: callbacks use the P1 per-IP general bucket (20 req/s, burst 40). **No new bucket** (spec §2.7; confirmed by the user on 2026-10-05 over the brief's "own bucket").
- Body limit stays 1 MB (`httpx.MaxBodyBytes`). The access log keeps logging the route pattern only, never the query.
- `PAYMENT_URL`, `LEDGER_URL` are required and validated at startup like the P1 upstream URLs. Compose already sets them (`deploy/docker-compose.yml:272-273`).

## Review Focus

1. A payment id that collides with a provider segment (`GET /api/payments/vnpay`) — it matches the Callback subtree; acceptable because ids are UUIDs, but the route test must pin that `/api/payments/{uuid}` stays User.
2. A **valid** buyer token on a callback route — must be proxied without identity headers (nothing injected), not just the invalid-token case.
3. Spoofed `X-User-Id` on a callback route — still stripped.
4. Non-canonical paths into the new prefixes (`/api/payments/stripe/../{id}`, `/api/seller/wallet/../products`) — 307/404 as in P1, never a downgrade to Callback/User.
5. Unknown method on a callback path (`CONNECT /api/payments/stripe/webhook`) — 404, as for every P1 route.
