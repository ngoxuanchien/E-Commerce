**Goal:** Fix the P1 follow-ups that P2 depends on before P2 starts.

**Sources:** the memory notes ws2-catalog-followups, ws3-order-followups, ws5-contract-followups and ws6-integration-followups.

## Task 2: optimistic concurrency for seller SKU stock

Decision: add an optional `SkuInput.expected_stock` (int32, ≥ 0) that works as compare-and-set. It is recorded in `services/catalog/README.md`.
- PATCH: every SKU with `id` must carry `expected_stock`, otherwise 400. SkuInput always carries `stock`, so any SKU edit writes stock.
- SKUs without `id` (new rows) and every POST must not set it (400).
- The value is compared with the locked row (`LockProductSkus ... FOR UPDATE`). A mismatch rolls back the whole PATCH with 409 `CONFLICT`.

Steps:
- [ ] Contract: add `expected_stock` to `SkuInput` in `api/openapi/catalog.yaml`, and add a 409 response to `updateSellerProduct`.
- [ ] catalog, red: domain validation tests (required with id on update; forbidden without id or on create). A store test covers a mismatch (409, nothing written) and a match (applied). A handler maps the error to 409.
- [ ] catalog, green: add `SkuInput.ExpectedStock` / `SkuChange.ExpectedStock`, check it in `applySkus`, and decode it in the HTTP layer.
- [ ] web, red: the PATCH body carries `expected_stock` equal to the loaded stock. A 409 reloads the form and shows a toast. The mock db enforces the rule.
- [ ] web, green: add `withExpectedStock` in product-schema, handle the 409 in ProductFormPage, and add stock to the form key.
- [ ] e2e client `SkuInput`: add `ExpectedStock` (omitempty).

## Task 3: order-svc reclaims orphaned idempotency rows

- [ ] Red (store): a key-less row older than `staleBefore` with the same request hash is reclaimed (`created=true`). The claim moves to the new time. A different hash, or a row that is not stale, is not reclaimed.
- [ ] Red (store): `CompleteIdempotencyKey` and `DeleteIdempotencyKey` affect only the caller's claim. A zombie run whose key was reclaimed gets `ErrIdempotencyClaimLost`, and its Tx rolls back.
- [ ] Red (app): with `ClaimTimeout` set, a checkout against an orphaned key older than the timeout succeeds instead of `ErrIdempotencyInProgress`.
- [ ] Green: add claim time to Begin/Complete/Delete, and add `CheckoutConfig.ClaimTimeout` (bootstrap: `PENDING_TIMEOUT + SWEEPER_INTERVAL`). Update the README decision list.
