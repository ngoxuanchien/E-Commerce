Six modules, one repo, no shared go.mod

The Go workspace is split into six modules so the five parallel workstreams each own one directory and never touch another’s dependency file.

Why six modules and not one

  • WS0 fixes every interface first; WS1–WS5 then run in parallel on separate branches, each editing only the directory it owns.
  • No two workstreams ever open the same go.mod, so no workstream can bump a dependency another workstream depends on.
  • Contract changes to api/, proto/ and pkg/ go through a dedicated PR to main; buf breaking blocks the breaking ones, and in-flight workstreams rebase afterwards.
  • CI runs go test -race -count=1 ./... as a matrix over the six modules, so a failure names the module that broke rather than a monolith.

Inside the four service modules

  • cmd/server/main.go — config, tracing, migrations, HTTP and gRPC servers, graceful shutdown.
  • internal/{domain,app,adapter/*} — pure domain, use cases, then http / grpc / postgres / redis / catalog / storage / kafka adapters.
  • migrations/ runs on startup; 000001_init.up.sql is a deliberate no-op baseline so the migrate path runs end to end.
  • sqlc.yaml is byte-identical in all four and points at internal/adapter/postgres/sqlcdb.

State of the tree

  • go.work, pkg/, gen/, proto/ and api/ exist today.
  • The four service skeletons are on disk; deploy/ and .github/ are not written yet.
  • gen/ is committed, so CI regenerates and fails on any diff.
