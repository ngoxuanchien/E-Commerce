One checkout, one trace

P1 success criterion 6, drawn as a span timeline: gateway, order and catalog in one trace, and the Kafka leg deliberately not in it.

What the test actually asserts

  • Drive a real checkout through the stack, then query Jaeger for that checkout’s trace_id — found via the request_id the gateway echoes back in X-Request-Id.
  • Assert the returned trace contains spans attributed to three services: gateway, order, and catalog. Missing any one of them fails the test.
  • Assert the gRPC ReserveStock call is among them — the criterion is the cross-service hop, not merely “the request has a trace”.
  • This is why the gateway opens its server span at step 2 of the auth pipeline, before anything else, and propagates traceparent on the proxy hop.

The async leg, honestly

  • A Kafka publish outlives the request, so it cannot be one continuous trace. The opt frame is the honest representation: the 201 has already been returned.
  • Note where the frame starts. Tx C — the status flip and the outbox row — happens inside the request and is a child of the checkout span. Only the relay’s publish and the consumer’s span sit after it.
  • What survives is the causal link. The writer’s context goes into the outbox row’s headers JSON, the relay publishes it, and traceparent rides as a Kafka header; the consumer extracts it and opens a SpanKindConsumer span named consume order.events.
  • So the OrderCreated publish and the later OrderCancelled release land as linked spans, joinable by trace id — but they are not children of the checkout span.

When the trace is thin

  • logx appends request_id, trace_id and span_id from the context to every line, so a log search works even when the span is not sampled.
  • The access log records method, path without query string, status, bytes and duration — never headers or bodies.
  • otelx installs the OTLP batcher only when the endpoint is non-empty; spans are still created and propagated either way, so a misconfigured exporter degrades to logs, not to silence.
