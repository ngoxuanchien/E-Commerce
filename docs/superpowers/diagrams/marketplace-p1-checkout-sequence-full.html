Checkout sequence

One POST /api/checkout turns a Redis cart into per-shop orders, reserving stock gRPC and rolling everything back if any reservation fails.

All-or-nothing is the whole point

  • Reserve is per order; if any one fails, every order of that checkout releases its stock and is marked CANCELLED.
  • Tx B writes cancel_reason = OUT_OF_STOCK or RESERVE_FAILED, actor system.
  • The buyer gets 409 with {shortages: [{sku_id, requested, available}]} — never a partial order.

Idempotency comes first

  • Idempotency-Key (1–100 chars) is required; the row stores sha256(body).
  • Same hash + stored response → replayed verbatim. Same hash in flight → 409 CONFLICT. Different hash → 422 IDEMPOTENCY_KEY_REUSED.
  • The stored response is written in Tx C, so a crash before it leaves the key re-runnable.

Grouping decides the shape

  • Lines are grouped by shop_id: one order per shop, SHIPPING_FEE_FLAT 30 000 VND each.
  • Totals use current catalog prices, and each item snapshots name, variant, image and unit price.
  • Tx A inserts PENDING rows, Tx C promotes them; the 2-minute sweeper catches a crash in between.
