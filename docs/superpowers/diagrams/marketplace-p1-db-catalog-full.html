catalog_db

Catalog tables, with the stock pair in focus.

Where the oversell guarantee lives

  • ReserveStock is one transaction: UPDATE skus SET stock = stock - $q WHERE id = $id AND active AND stock >= $q.
  • Zero rows updated is a shortage; the transaction rolls back and nothing is reserved.
  • stock_reservations makes the call idempotent per order_id, keyed (order_id, sku_id).
  • ReleaseStock takes FOR UPDATE on status='reserved' rows, adds quantities back, then flips them to released.
  • Editing stock sets on-hand directly and deliberately does not touch reservations.

Search, browse and the indexes

  • search_vector is GENERATED ALWAYS AS (...) STORED, so it can never drift from name/description.
  • GIN (search_vector) serves websearch_to_tsquery('simple', vn_unaccent(q)); "ao thun" finds "Áo thun".
  • (status, created_at desc, id) and (status, min_price, id) back the two keyset sorts; the cursor is {sort_value, id}.
  • Browse returns only active products with at least one active SKU; min_price is the lowest active-SKU price.

Boundaries, omissions, and status

  • No FK from stock_reservations.order_id to orders — that is a cross-service boundary, enforced in code.
  • P1 allows at most one shop per user, so owner_user_id is UNIQUE; slug is also UNIQUE and immutable after create.
  • product_images is capped at 9 per product; a SKU missing from an update is deactivated, never deleted.
  • Not drawn: processed_events, and product_images.product_id → products.id (both exist in the spec DDL).
  • All of this is spec-level DDL — services/*/migrations are still SELECT 1 baselines.
