Service dependency graph

Who calls whom across the four services, with the catalog-to-identity back-edge that makes this a graph rather than a tree.

The cycle is the story

  • catalog → identity (GrantRole on shop open) opposes order → catalog, so the graph has no topological order.
  • The two nodes keep normal treatment; only the back-edge is accent, so the eye lands on the relationship, not the boxes.
  • Breaking it would need an events-based role grant — out of scope for P1.

Fan-in concentrates on gateway

  • Gateway carries three inbound callers; Postgres is depended on by all three services, but never crosses a network boundary.
  • Badges count callers, so gateway and Postgres are the two convergence points.
  • A tree could not show either convergence — that is why this is a graph.

Sync, async and telemetry

  • REST (link-blue): web → gateway and gateway → each service.
  • gRPC (solid muted): order → catalog, 3 s timeout, retry ≤2 on UNAVAILABLE.
  • Kafka (dashed): order.events, key order_id; catalog consumes only OrderCancelled.
