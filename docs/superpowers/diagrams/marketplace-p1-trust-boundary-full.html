Architecture · 2026-09-28

P1 trust boundary

web → gateway :8080 is the only application ingress, so a host port map makes the boundary checkable rather than aspirational.

Why the services trust X-User-Id

  • Host ports: gateway 8080:8080, web 3000:80 (container listens on :80). Those two are the entire application ingress.
  • The gateway always strips an inbound X-User-Id / X-User-Roles, verifies RS256 via JWKS, then re-injects sub and roles — a client cannot spoof identity.
  • An invalid token is 401 even on a public route: the gateway fails loudly rather than degrading to anonymous.
  • Everything else is unreachable from the host, so the implicit trust is a consequence of the port map, not a convention.

One instance, three databases

  • One postgres:17 instance; deploy/postgres/init.sql creates identity_db, catalog_db and order_db.
  • The rule that keeps it honest: no service reads another's database, so co-location buys no coupling.
  • The gateway has no database at all — no pgx in its go.mod, no migrations/ — and it is the only service that never starts a gRPC server.
  • All four images are gcr.io/distroless/static-debian12:nonroot with ENTRYPOINT ["/server"]: nothing to compromise in the image.

Keys, JWKS and the spec's honesty

  • make keys writes an RSA 2048 deploy/secrets/jwt_private.pem (gitignored); identity mounts it read-only at /run/secrets/jwt_private.pem.
  • MinIO is minioadmin, Postgres is marketplace, and the gateway also holds CORS_ALLOWED_ORIGINS and TRUSTED_PROXIES — the AUTH line reaches secrets, not one tool.
  • JWKS is fetched at startup, cached, refreshed every 5 min and on an unknown kid at most once per 30 s. That endpoint is internal-only and not routed by the gateway: a read-only identity edge, not a bypass.
  • deploy/ does not exist in the repo yet — this is the specified topology, not an observed one.
