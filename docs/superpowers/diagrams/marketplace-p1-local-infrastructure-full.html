Local stack: four ports reach the host

The specified Compose topology publishes only the gateway, the web container, Jaeger UI and MinIO — which is exactly why the services trust X-User-* headers.

What reaches the host, and what does not

  • Published: 8080:8080 (gateway), 3000:80 (the web container listens on :80; 3000 is the host side), 16686:16686 (Jaeger UI), 9000:9000 and 9001:9001 (MinIO API and console).
  • Not published: identity 8081/9081, catalog 8082/9082, order 8083/9083, Postgres, Redis, Kafka — and Jaeger’s OTLP 4317, which is the counter-intuitive one.
  • That single fact is the whole authorization model: only the gateway is reachable, so it strips any inbound X-User-Id / X-User-Roles and sets fresh ones. Everything downstream trusts those headers by construction.
  • CORS origins list both :3000 and the Vite dev server :5173.

Startup, health, and order

  • /healthz and /readyz are registered outside the middleware chain, so they answer even when auth or rate limiting is unhappy.
  • /readyz runs its named dependency checks concurrently under a 2s budget and returns 200 or 503.
  • The container healthcheck is the binary’s own argv subcommand — ["CMD","/server","healthcheck"], 5s interval, 3s timeout, 20 retries, 5s start period — not curl.
  • Migrations run on startup, so a fresh make up-app needs no separate migrate step.

Dependency order and init jobs

  • identity, catalog and order wait for Postgres to be healthy; order also waits for Redis.
  • catalog additionally waits for kafka-init and minio-init to have completed successfully.
  • gateway waits for all three services healthy; web waits for gateway healthy.
  • The init jobs exist because both stores have auto-create disabled: kafka-topics.sh --create --topic order.events --partitions 3 --replication-factor 1 and mc mb --ignore-existing plus mc anonymous set download on product-images.
