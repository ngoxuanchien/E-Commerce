Database schema · 2026-09-28

identity_db

Three tables: accounts, roles, and refresh rotation.

Refresh rotation, in three columns

  • family_id chains every token issued from one login session.
  • /refresh revokes the old row, inserts a new one in the same family, and sets replaced_by.
  • Reusing an already-revoked token revokes the whole family and answers 401 — that is the theft signal.
  • token_hash is bytea UNIQUE: 32 random bytes base64url to the client, SHA-256 digest at rest.

Column semantics

  • email is citext, so login is case-insensitive without a functional index.
  • revoked_at and replaced_by are NULL on a live token and set together on rotation.
  • user_roles is keyed (user_id, role); CHECK limits role to buyer, seller, admin.
  • Access tokens are stateless RS256 — nothing about them reaches this database.

What the DDL does not say

  • migrations/000001 are no-op SELECT 1 baselines; these tables land in WS1 as 000002+.
  • The spec DDL declares no ON DELETE action on either child FK — delete semantics are undecided.
  • admin is in the CHECK but unreachable in P1; no role is ever granted for it.
  • Logout always 204 and revokes the family server-side, not by row count alone.
